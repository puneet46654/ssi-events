# Data model — DynamoDB table `ssi-events`

One table, on-demand billing, in ap-south-1. It's only accessed by the backend Lambda (`ssi-events-api`, role `ssi-events-api`).

| Setting | Value |
| --- | --- |
| Keys | `PK` (partition), `SK` (sort), both strings |
| Indexes | `GSI1` (`GSI1PK`, `GSI1SK`) and `GSI2` (`GSI2PK`, `GSI2SK`), both projecting all attributes |
| TTL | attribute `ttl` (epoch seconds); DynamoDB deletes expired items, usually within a few days |
| Backups | point-in-time recovery, 35 days |
| Protection | deletion protection on; encrypted at rest (AWS-owned key) |

Key builders live in `backend/src/db/table.ts`. Keep this file and that one in step.

## Access patterns

| Need | How |
| --- | --- |
| Event with all days and slots | `Query PK = EVENT#id` (one request) |
| Slots for one day | `Query PK = EVENT#id, SK begins_with SLOT#<nn>#` |
| Public catalogue by date | `Query GSI1 PK = EVENTS` (range on start date) |
| Booking by reference | `GetItem BOOKING#ref / META` |
| Bookings for an event, by day/slot | `Query GSI1 PK = EVENT#id#BOOKINGS` |
| My Tickets by mobile number | `Query GSI2 PK = PHONE#<number>` |
| Attendance for an event | `Query GSI1 PK = EVENT#id#BOOKINGS` (filter `attendanceStatus`) |
| Admin login | `GetItem ADMIN#username / META` |
| Polling for changes | `GetItem REALTIME / GLOBAL` (CDN-cached 2 s) |

## Booking without overselling

A booking is one `TransactWriteItems` with four parts. Either all four are written or none are.

1. **Update the slot:** `bookedCount = bookedCount + 1`, on condition `bookedCount < capacity`.
2. **Put the booking:** on condition `attribute_not_exists(PK)`.
3. **Put the request key:** `REQUEST#<hash>` → bookingId, on condition `attribute_not_exists(PK)`.
4. **Update the event:** `bookedSlots = bookedSlots + 1`. The event item keeps `totalSlots` and `bookedSlots`, so the catalogue (`GET /api/events`) needs one query and never sums slots.

If the request key already exists, it's a retry. The backend then returns the booking that was already confirmed instead of creating a second one. If the slot is full, the backend returns `409`. Cancelling or rescheduling reverses the slot counters in the same kind of transaction.

## Not stored here

- **Event images:** stored in S3 bucket `ssi-studio-events` (prefix `events/`). The item stores only the object key.
- **Secrets** (session/ticket signing keys): stored in SSM Parameter Store `/ssi-events/*` and copied to the backend's environment by `infra/set-secrets.sh`.

## Item attributes (implemented)

| Item | Attributes |
| --- | --- |
| Event | `eventId`, `eventName`, `eventType`, `bookingFormTemplate`, `venue`, `description`, `imageKey` (S3 key), `numberOfDays`, `startDate`/`endDate` (`YYYY-MM-DD`), `timeZone`, `status` (`ACTIVE` or `CANCELLED`; `LIVE`/`UPCOMING`/`COMPLETED` is computed when read), `totalSlots`, `bookedSlots`, `editLock` (epoch ms, present only while an edit runs), `createdBy`, `createdAt`, `updatedAt` |
| Day schedule | `dayId`, `dayNumber`, `date`, `startTime`, `endTime`, `lunchEnabled`, `lunchStart`, `lunchEnd`, `slotDuration`, `slotGap`, `capacity`, `sameAsDay1` (numbers stored as numbers) |
| Slot | `slotId`, `dayId`, `dayNumber`, `date`, `startTime`, `endTime`, `capacity`, `bookedCount` |
| Admin user | `username`, `name`, `role` (`superadmin`, `admin` or `staff`), `permissions[]`, `canCreate`, `canDelete`, `isActive`, `passwordHash` + `passwordSalt` (scrypt, 64-byte key, 16-byte salt), `createdBy`, `createdAt`, `updatedAt`, `lastLoginAt` |
| Admin activity | `admin`, `action`, `resource`, `resourceId`, `details` (sensitive keys removed), `createdAt` |

**Event edit** takes the edit lock on the event item, then writes each day and slot with its own condition: kept slots change capacity only while `bookedCount <= capacity`, and removed slots are deleted only while `bookedCount = 0`. Booking and reschedule transactions refuse to run while the lock is held. The event item is updated last, which also removes the lock. Slot sort keys keep the day number they were created with; a booked day can't change its number.

**Event deletion** deletes the event item first, on condition `bookedSlots = 0`. Without the event item, no booking can be created, so the remaining items under `EVENT#<id>` are then batch-deleted.

**Admin login ID change** moves the item (`ADMIN#<old>` → `ADMIN#<new>`) in one transaction.

**Event creation** writes the day and slot items first, in batches of 25, and the event item last. A create that fails midway leaves no event in the catalogue; its orphaned day and slot items are never read.
